大多数 Agent 架构，不是在解决业务问题。是在替当前模型的短板兜底。

我现在看一个 Agent 方案，只问一个问题：

**下一代模型把规划、工具调用和长上下文再往前推一步，这层东西还必须存在吗？**

如果答案是否定的，它就不该被当成长期架构，更不该被包装成公司的 AI 护城河。

这不是说 Planner、Router、Reflection、Critic 没有用。它们当然有用——今天的模型确实会漏步骤、选错工具、在长任务里跑偏。

问题在于，我们太容易把“今天有用”误读成“以后必须有”。

模型不会规划，于是加一个 Planner。

模型不会选工具，于是加一个 Router。

模型输出不稳定，于是再挂一个 Critic。

一个模型不放心，就让三个模型开会。

每一步单独看都合理。拼起来之后，原本应当先用强模型验证的问题，变成了一套要维护状态、传递上下文、处理失败、做 tracing、写 eval 的分布式系统。

这就是我不太相信大部分 Agent Infra 的原因。

它解决的往往不是业务世界固有的复杂性，而是模型在某个版本上的能力缺口。能力缺口会变，系统留下来。

模型升级一次，原来需要拆成三步的任务可以一步完成。你留下的却是三层协议、三份日志、三组失败路径，以及一群已经习惯围着这些组件组织工作的工程师。

**最危险的架构决策，是把模型今天的缺陷写进公司明天的系统。**

这条判断有个很清楚的边界。

权限、交易、审计、私有数据、业务状态、异步任务、并发执行、工具的副作用——这些不会因为模型更聪明就自动消失。它们属于 Environment，是工程该投入的地方。

但“让模型先想一遍、再让另一个模型检查一遍、还不放心就开个会”不是同一回事。没有权限边界、并发任务或 Context 隔离，就别把三个模型轮流说话叫 Multi-Agent。

那不是协作。多数时候，只是昂贵的角色扮演。

所以我会把优先级倒过来：先买当前能用到的最强模型；先把完整、正确、有权限的 Context 和工具给它；先验证一条薄工作流能不能完成任务。

只有在真实的边界出现时，再增加状态机、路由、隔离和协作单元。

不要先造一个复杂的 Agent 系统，再希望模型配得上它。

**不要给模型造大脑。给模型造眼睛、手和钥匙。**

你们团队最近投入最多的 Agent 组件里，哪些在模型能力再上一个台阶后仍然必须存在？哪些其实只是把短期焦虑编译成了长期维护成本？
